# IMU 热插拔改造小计划

本文档记录当前 `f103c8t6_mini` 工程下，IMU 热插拔与故障隔离的后续改造方向。

当前决定：

- 暂不在 F103C8T6 版本继续落代码。
- 原因是当前工程已经非常接近 `FLASH` 上限，继续加入热插拔状态机、I2C 恢复和重扫逻辑，风险较高。
- 等后续更换更大容量芯片后，再继续实现。

## 1. 当前现状

目前 IMU manager 的行为可以概括为：

- 启动时对固定地址 `0x50 / 0x51 / 0x52 / 0x53` 做初始化和一次 probe。
- 运行时按槽位顺序采集 IMU。
- 单个槽位读失败时，本帧只会让该槽位 `valid_mask` 失效。
- 当前没有完整的运行时离线标记和后台重扫机制。

现阶段已知问题：

- 某个 IMU 插拔或故障时，可能把后续槽位也拖失败一轮，表现为“掉两个”。
- 启动时未探测到的 IMU，不会在运行中自动重新发现。
- 缺少明确的 online/offline 状态切换。

## 2. 改造目标

后续改造建议同时解决这两类问题：

1. 故障隔离：尽量做到“只掉自己”，不要影响其他 IMU。
2. 热插拔恢复：掉线后自动标记离线，重新插上后自动恢复上线。

## 3. 建议方案

### 3.1 槽位级状态管理

为每个 IMU 槽位维护独立状态：

- `online_mask`
- 连续失败计数
- 下次允许重扫的时间戳

设计原则：

- 单次失败只影响本槽位当前帧数据。
- 连续失败达到阈值后，才把该槽位置为 offline。
- 成功读到数据后，清零该槽位失败计数。

### 3.2 运行时故障隔离

采集循环按槽位处理：

- 某个槽位读失败后，不立即让整个采集回合退出。
- 优先尝试把故障限制在当前槽位。
- 如果确认 I2C 外设状态异常，再做一次受控的总线恢复。

注意：

- 总线恢复不能绑在每一次失败上，否则容易重新引入“掉两个甚至全掉”的副作用。
- 更稳妥的做法是“单槽位失败计数 + 必要时恢复总线”。

### 3.3 后台低频重扫

对 offline 槽位增加低频 probe：

- 例如每 `200~500 ms` 扫一次。
- probe 成功后重新执行初始化收尾动作。
- 重新置位 `online_mask`，让该槽位重新参与正常采集。

probe 成功后的恢复动作建议至少包括：

- 重新读关键寄存器确认设备存在。
- 重新执行当前初始化里已有的配置步骤。
- 必要时重新下发 `SetAxis9()` 等模式配置。

### 3.4 启动阶段保持固定地址 probe

当前工程仍是固定地址模型，不需要上升到“全总线动态发现”：

- 启动时继续针对 `0x50 / 0x51 / 0x52 / 0x53` 做 probe。
- 运行时对这些固定槽位做离线重扫即可。

这样改动范围更可控，也更符合当前硬件连接方式。

## 4. 实施顺序

建议后续按下面顺序推进：

1. 先做槽位级失败计数和离线阈值。
2. 再做“只掉自己”的故障隔离。
3. 再补离线槽位的低频重扫。
4. 最后再评估是否需要更激进的 I2C 总线恢复策略。

## 5. 验证项

后续落地后，重点验证这几项：

1. 拔掉任意一个 IMU，其余 IMU 仍持续采集和发包。
2. 被拔掉的 IMU 在连续失败后会被标记为 offline。
3. 重新插回同地址 IMU 后，系统会自动恢复该槽位数据。
4. 故障 IMU 不再连带造成后续槽位同时丢失。
5. 在高频采集和 UART bridge 同时运行时，系统仍稳定。

## 6. 暂停原因记录

本次尝试过程中，功能方案本身是成立的，但在当前 F103C8T6 目标下继续加代码，已经不适合：

- `FLASH` 余量过小。
- 后续继续加状态机、恢复逻辑和诊断输出，大概率还会继续增大体积。
- 因此选择先暂停，待更换芯片后再继续实现，是合理决策。
